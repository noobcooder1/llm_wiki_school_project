# ADR-003: 마크다운 기반 지식 내보내기 채택

## 결론
LLM Wiki는 저장된 AI 대화를 마크다운 문서로 내보내는 방식을 기본 내보내기 전략으로 채택한다.

이 결정을 한 이유는 마크다운이 Obsidian, GitHub, VS Code, Notion 등 다양한 도구에서 읽고 편집할 수 있는 범용 텍스트 포맷이기 때문이다. 사용자는 앱을 벗어나도 자신의 AI 대화를 장기 보관하고 재가공할 수 있으며, 특정 앱에 데이터가 묶이는 종속 문제를 피할 수 있다.

## 결정 ---(좀 더 자세한 이유)
LLM Wiki는 마크다운 기반 내보내기 시스템을 채택한다.

모든 대화는 다음 요소를 포함한 마크다운 문서로 내보낼 수 있어야 한다.

- 제목
- 프로젝트 이름
- 생성/수정 날짜
- 태그
- 대화 요약
- 사용자 메시지와 AI 응답
- 코드 스니펫
- 원본 AI provider 및 모델 정보
- 필요한 경우 YAML Frontmatter

기본 내보내기 형식은 마크다운이다.

## 결정 이유
마크다운을 선택한 이유는 호환성, 장기 보관성, 사용자의 데이터 소유권 때문이다.

마크다운은 특정 회사나 특정 앱에 종속되지 않는 텍스트 기반 포맷이다. Obsidian, GitHub, Notion, VS Code, 정적 사이트 생성기 등 많은 도구에서 읽을 수 있다. 사용자는 LLM Wiki에서 저장한 대화를 앱 밖에서도 계속 활용할 수 있다.

AI 대화는 시간이 지나면 단순 로그가 아니라 설계 근거, 학습 노트, 디버깅 기록, 코드 참고 자료가 된다. 마크다운은 이런 정보를 문서화하기에 충분히 단순하면서도 제목, 목록, 코드 블록, 링크, 태그를 표현할 수 있다.

또한 마크다운 내보내기는 로컬 우선 전략과 잘 맞는다. 사용자는 클라우드 동기화를 사용하지 않더라도 자신의 데이터를 파일로 백업할 수 있고, Git을 통해 변경 이력을 관리할 수 있다.

## 상태
채택됨

## 배경
LLM Wiki의 핵심 목적은 AI와 나눈 대화를 일회성 소비로 끝내지 않고, 장기적으로 축적 가능한 지식 자산으로 만드는 것이다.

사용자는 저장한 대화를 앱 안에서 검색하는 것뿐 아니라 다음과 같은 방식으로 활용하고 싶어할 가능성이 높다.

- Obsidian 같은 개인 지식 관리 도구에 보관
- Git 저장소에 기록하고 버전 관리
- Notion, Google Docs, 블로그 등으로 재가공
- 프로젝트 문서나 학습 노트로 재사용
- 앱을 더 이상 사용하지 않더라도 자신의 데이터를 계속 보관

만약 앱 내부 전용 포맷만 제공하면 다음 문제가 발생한다.

- 사용자가 자신의 데이터를 다른 도구로 옮기기 어렵다.
- 앱에 데이터가 묶여 장기적으로 이동성이 떨어진다.
- 장기 보관성과 호환성이 낮아진다.
- Obsidian, Git, 정적 사이트 생성기 등 텍스트 기반 생태계와 연동하기 어렵다.


# SQLite 로컬 저장 구조 정리

## 요약

LLM Wiki의 대화, 메시지, 태그 데이터를 로컬 SQLite에 저장하기 위한 구조를 정리한 대화.

## 대화

### 사용자

conversations, messages, tags 테이블을 이용해서 AI 대화를 저장하는 구조를 설계해줘.

### AI

대화 단위는 conversations 테이블에 저장하고, 각 발화는 messages 테이블에 순서대로 저장하는 구조가 적합합니다. 태그는 tags 테이블로 분리하고 conversation_tags 연결 테이블을 두면 하나의 대화에 여러 태그를 연결할 수 있습니다.

## 코드 스니펫

```sql
CREATE TABLE conversations (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  title TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```
````

## 검토한 대안
### JSON 내보내기
구조화된 데이터를 보존하기 좋고 다시 앱으로 가져오기 쉽다.

하지만 일반 사용자가 읽기 어렵고, Obsidian이나 문서 작성 도구에서 바로 활용하기 어렵다. 백업/복원용 보조 포맷으로는 적합하지만 기본 내보내기 포맷으로는 마크다운보다 약하다.

### PDF 내보내기
읽기와 공유에는 편하지만 재편집, 검색, 코드 재사용, Git 버전 관리에는 불리하다.

보고서 형태의 공유 기능으로는 의미가 있지만, 개인 지식 자산의 원본 포맷으로는 적합하지 않다.

### 앱 전용 포맷
앱 내부 기능을 가장 풍부하게 표현할 수 있다.

하지만 데이터 이동성이 낮고 특정 앱에 데이터가 묶이는 문제가 발생한다. LLM Wiki의 제품 철학과 맞지 않는다.

### 마크다운 내보내기
읽기 쉽고, 편집 가능하며, 다양한 지식 관리 도구와 호환된다.

LLM Wiki의 장기 지식화 목적에 가장 적합하다.

## 예상 구현
첫 번째 개발 단계에서는 다음 기능을 제공한다.

- 전체 대화 마크다운 내보내기
- 프로젝트 단위 내보내기
- 제목, 프로젝트, 날짜, 태그 포함
- 사용자/AI 메시지 구분
- 코드 블록 보존
- 자동 추출된 코드 스니펫 섹션 생성
- 클립보드 복사 또는 파일 저장

두 번째 개발 단계 이후에는 다음 기능을 고려한다.

- Obsidian Vault 직접 동기화
- YAML Frontmatter 커스터마이징
- 태그 네이밍 규칙 설정
- 이미지, 첨부파일, 링크 자산 내보내기
- 마크다운 가져오기를 통한 복원

## 영향
### 장점
- Obsidian, GitHub, VS Code 등 다양한 도구와 연동 가능하다.
- 사용자가 앱 밖에서도 자신의 데이터를 읽고 편집할 수 있다.
- 장기 보관에 적합하다.
- Git 기반 버전 관리가 가능하다.
- 로컬 우선 구조에서 백업 수단으로 사용할 수 있다.

### 단점
- 이미지, 음성, 파일 첨부 등 멀티미디어 표현은 별도 규칙이 필요하다.
- 복잡한 대화 구조나 그래프 관계를 마크다운만으로 표현하기 어렵다.
- 실시간 협업 기능에는 적합하지 않다.
- 마크다운 내보내기와 앱 내부 DB 간 동기화 규칙을 별도로 설계해야 한다.

## 리스크 대응
- 기본 마크다운은 사람이 읽기 쉬운 형태로 유지한다.
- 구조적 재가져오기가 필요한 데이터는 YAML Frontmatter와 JSON 내보내기를 함께 고려한다.
- 이미지와 첨부파일은 `assets/` 폴더와 상대 경로 규칙을 별도로 정의한다.
- Obsidian 동기화를 두 번째 개발 단계 개발 계획에 포함해 마크다운의 활용성을 높인다.

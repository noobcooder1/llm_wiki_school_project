# ADR-001: 로컬 우선 구조 채택

## 결론
LLM Wiki는 사용자 대화 데이터를 서버가 아니라 사용자 디바이스에 먼저 저장하는 로컬 우선 아키텍처를 채택한다.

이 결정을 한 이유는 AI 대화 데이터가 개인 지식, 업무 내용, 코드, API 키 등 민감한 정보를 포함할 수 있기 때문이다. 로컬 우선 구조를 사용하면 사용자 데이터 통제권을 강화하고, 오프라인 사용성을 확보하며, 초기 서버 운영 비용과 보안 책임을 줄일 수 있다.

## 결정 ---(좀 더 자세한 이유)
LLM Wiki 앱은 Local-first Architecture를 채택한다.

기본 원칙은 다음과 같다.

- 모든 대화 데이터는 기본적으로 사용자 디바이스 내부에 저장한다.
- 첫 번째 개발 단계에서는 서버에 사용자 대화 로그를 저장하지 않는다.
- 로컬 데이터베이스는 SQLite를 사용한다.
- API 키와 DB 암호화 키 등 민감한 값은 Secure Storage를 통해 저장한다.
- 클라우드 동기화는 두 번째 개발 단계 이후 선택 기능으로 제공한다.
- 클라우드 동기화를 제공할 경우 End-to-End Encryption(E2EE)을 전제로 한다.

즉, 앱의 기본 동작은 "사용자의 지식은 사용자의 기기에 먼저 저장된다"는 정책을 따른다.

## 결정 이유
Local-first를 선택한 가장 큰 이유는 개인정보 보호와 사용자 신뢰 때문이다.

LLM Wiki는 단순 메모 앱이 아니라 AI 대화를 장기적으로 축적하는 지식 저장소다. 사용자가 회사 업무, 개인 프로젝트, 코드, 전략, 학습 내용 등을 AI와 대화한 뒤 저장할 가능성이 높다. 이런 데이터가 앱 서버에 자동 저장된다면 사용자는 제품을 신뢰하기 어렵다.

또한 초기 제품에서는 서버 저장 기능보다 "빠르게 저장하고, 검색하고, 내보내는 경험"이 더 중요하다. 로컬 저장 구조를 사용하면 네트워크 요청 없이 빠르게 대화 목록과 검색 결과를 보여줄 수 있고, 오프라인에서도 앱을 사용할 수 있다.

운영 관점에서도 서버 저장을 최소화하면 초기 비용과 보안 책임을 줄일 수 있다. 특히 대화 로그를 서버에 저장하지 않으면 데이터 유출 사고 발생 시 피해 범위를 크게 줄일 수 있다.

## 상태
채택됨

## 배경
LLM Wiki 앱은 사용자가 AI와 나눈 대화를 저장하고, 프로젝트별로 분류하며, 검색 가능한 개인 지식 자산으로 관리하는 앱이다.

이 앱에서 다루는 데이터는 단순한 채팅 기록이 아니라 다음과 같은 민감 정보를 포함할 수 있다.

- 사용자의 업무 아이디어, 학습 기록, 개인 연구 내용
- 코드, 설계 문서, 디버깅 과정, 제품 기획 내용
- OpenAI 등 외부 AI 서비스 호출에 필요한 API 키
- 이메일, 계정 정보, 프로젝트 이름, 내부 문서 일부

만약 모든 데이터를 서버 중심 구조로 저장하면 다음 문제가 발생할 수 있다.

- 사용자의 대화 로그가 서비스 운영 서버에 남아 개인정보 유출 위험이 커진다.
- 서버 저장소, 백업, 보안, 암호화, 접근 제어를 모두 운영해야 하므로 비용과 책임 범위가 커진다.
- 사용자는 자신의 AI 대화가 어디에 저장되는지 명확히 알기 어렵고, 서비스 신뢰도가 낮아질 수 있다.
- 네트워크가 불안정하거나 오프라인 상태일 때 앱의 핵심 기능을 사용할 수 없다.
- 초기 제품 단계에서 서버 동기화까지 포함하면 구현 범위가 커져 첫 번째 개발 단계 출시 속도가 느려진다.

LLM Wiki의 핵심 가치는 "AI 대화를 개인의 장기 지식 자산으로 축적하는 것"이다. 따라서 사용자가 자신의 데이터를 직접 통제할 수 있다는 신뢰가 제품의 핵심 경쟁력이 된다.


## 검토한 대안
### 서버 우선 아키텍처
모든 데이터를 서버에 저장하고 앱은 서버 API를 통해 데이터를 읽고 쓰는 방식이다.

이 방식은 멀티 디바이스 동기화와 백업은 쉽지만, 사용자 대화 로그를 서버에 저장해야 한다. 개인정보 보호, 서버 비용, 보안 운영 부담이 커지기 때문에 첫 번째 개발 단계 구조로는 적합하지 않다.

### 하이브리드 아키텍처
로컬과 서버에 동시에 데이터를 저장하는 방식이다.

장기적으로는 좋은 방향일 수 있지만, 첫 번째 개발 단계에서 구현하면 동기화 충돌 처리, 암호화, 백업 정책, 장애 복구 등 고려해야 할 범위가 커진다. 따라서 두 번째 개발 단계 이후 선택적 Cloud Sync 기능으로 확장하는 것이 적절하다.

### 로컬 우선 아키텍처
기본 데이터는 로컬에 저장하고, 클라우드 기능은 사용자가 명시적으로 선택할 때만 제공하는 방식이다.

LLM Wiki의 보안 요구사항과 초기 제품 범위에 가장 적합하다.

## 예상 구현
첫 번째 개발 단계 구현에서는 다음 구조를 예상한다.

- `conversations` 테이블: 대화 단위 저장
- `messages` 테이블: 사용자/AI 메시지 저장
- `tags` 테이블: 자동 생성 및 수동 입력 태그 저장
- `conversation_tags` 테이블: 대화와 태그의 관계 저장
- SQLite 기반 로컬 저장
- SQLCipher를 통한 DB 파일 암호화
- Secure Storage를 통한 DB 암호화 키 저장
- 네트워크 없이 제목, 본문, 태그 검색 가능

두 번째 개발 단계 이후에는 다음 기능을 고려한다.

- 사용자가 선택한 경우에만 Cloud Sync 활성화
- 동기화 데이터는 E2EE 적용
- Obsidian, Git, Drive 등 외부 저장소 연동
- 멀티 디바이스 충돌 해결 정책 도입

## 영향
### 장점
- 사용자 대화 로그를 서버에 저장하지 않아 개인정보 보호 수준이 높다.
- 네트워크 없이도 앱의 핵심 기능을 사용할 수 있다.
- 검색, 목록 조회, 마크다운 내보내기가 빠르게 동작한다.
- 초기 서버 비용과 보안 운영 부담이 줄어든다.
- "내 지식은 내 기기에 있다"는 명확한 제품 메시지를 만들 수 있다.

### 단점
- 디바이스를 분실하거나 앱을 삭제하면 데이터 손실 위험이 있다.
- 여러 기기 간 자동 동기화가 어렵다.
- 백업/복원 기능을 별도로 설계해야 한다.
- 로컬 DB 암호화와 키 관리 구현이 필요하다.

## 리스크 대응
- 첫 번째 개발 단계부터 마크다운 내보내기를 제공해 사용자가 직접 백업할 수 있게 한다.
- SQLCipher와 Secure Storage를 사용해 로컬 데이터 보호 수준을 높인다.
- 두 번째 개발 단계에서 E2EE 기반 Cloud Sync를 선택 기능으로 제공한다.
- 앱 삭제 전 백업 안내, 정기 Export 알림 등을 추가로 고려한다.

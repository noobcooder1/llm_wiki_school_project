# ADR-004: 플러터 기반 크로스 플랫폼 개발 채택

## 결론
LLM Wiki는 클라이언트 앱 개발 기술로 플러터를 채택한다.

이 결정을 한 이유는 플러터가 하나의 코드베이스로 iOS, Android, Web, Desktop까지 확장할 수 있기 때문이다. LLM Wiki는 모바일에서 빠르게 AI 대화를 저장하고, 웹이나 데스크탑에서 검색과 마크다운 내보내기를 활용할 가능성이 높은 제품이므로, 초기 개발 속도와 장기 플랫폼 확장성을 동시에 확보할 수 있는 플러터가 적합하다.

## 결정 ---(좀 더 자세한 이유)
LLM Wiki 앱의 클라이언트 개발 환경으로 플러터를 채택한다.

플러터를 선택한 범위는 다음과 같다.

- iOS 앱 개발
- Android 앱 개발
- Web 프로토타입 및 관리 화면 확장
- 향후 Desktop 앱 확장 가능성 확보
- 단일 코드베이스 기반 UI 개발

## 결정 이유
플러터를 선택한 가장 큰 이유는 하나의 코드베이스로 iOS, Android, Web, Desktop까지 확장할 수 있기 때문이다.

LLM Wiki는 개인 지식 관리 앱이다. 사용자는 모바일에서 빠르게 AI 대화를 저장하고, 나중에 더 큰 화면에서 검색하거나 마크다운으로 내보내고 싶어할 수 있다. 플러터는 이런 멀티 플랫폼 제품 방향에 잘 맞는다.

또한 플러터는 UI 일관성이 높다. 프로젝트 목록, 태그 필터, 검색, 대화 상세, 마크다운 미리보기, 보안 설정처럼 복잡한 화면을 플랫폼별로 따로 구현하지 않고 공통 컴포넌트로 관리할 수 있다.

개발 속도 측면에서도 장점이 있다. V1에서는 제품 가설 검증이 중요하므로 iOS와 Android를 별도 네이티브 코드로 구현하는 것보다 플러터로 빠르게 기능을 완성하는 것이 유리하다.

로컬 저장소와 보안 기능 측면에서도 플러터 생태계는 SQLite, Secure Storage, Biometric Auth, 파일 저장, 공유 기능 등 모바일 앱에 필요한 플러그인을 제공한다. 따라서 PRD의 핵심 요구사항을 구현하기에 충분하다.

## 상태
채택됨

## 배경
LLM Wiki는 모바일 앱으로 시작하지만, 제품 특성상 장기적으로 여러 플랫폼에서 사용할 가능성이 높다.

사용자는 AI 대화를 다음 환경에서 저장하고 활용하고 싶어할 수 있다.

- iPhone 또는 Android 스마트폰에서 빠르게 대화 저장
- 태블릿에서 긴 대화 읽기와 정리
- 웹에서 검색과 Export 작업
- 데스크탑 앱에서 Obsidian, Git, 로컬 파일 시스템과 연동

따라서 초기 기술 스택은 모바일 중심이면서도 웹과 데스크탑 확장 가능성을 가져야 한다.

PRD에서는 기술 스택으로 플러터, SQLite, Secure Storage, OpenAI SDK를 제안한다. 이 중 플러터는 UI와 앱 구조의 중심이 되는 선택이다.


## 검토한 대안
### 네이티브 iOS + 네이티브 Android
Swift/SwiftUI와 Kotlin/Jetpack Compose로 각각 구현하는 방식이다.

플랫폼별 최적화와 네이티브 기능 접근성은 가장 좋지만, 동일한 기능을 두 번 구현해야 한다. 초기 개발 속도가 느리고 유지보수 비용이 높다.

### React Native
JavaScript/TypeScript 생태계를 활용할 수 있고 크로스 플랫폼 개발이 가능하다.

웹 개발자에게 친숙하지만, 네이티브 모듈 의존성과 버전 호환성 문제가 발생할 수 있다. LLM Wiki처럼 로컬 DB, 암호화, Secure Storage, 파일 Export 등 네이티브 기능을 많이 쓰는 앱에서는 플러그인 안정성을 면밀히 봐야 한다.

### Web App/PWA 우선 개발
웹으로 빠르게 배포할 수 있고 설치 장벽이 낮다.

하지만 iOS/Android의 Secure Storage, 로컬 DB 암호화, 생체 인증, 파일 시스템 접근 등에서 네이티브 앱보다 제약이 있다. PRD의 보안 요구사항을 만족하기 어렵다.

### 플러터
모바일 앱 품질을 유지하면서 단일 코드베이스로 여러 플랫폼을 지원할 수 있다.

LLM Wiki의 V1 개발 속도와 장기 플랫폼 확장성 사이에서 가장 균형이 좋다.

## 예상 구현
플러터 앱은 다음 구조로 발전시킨다.

- `lib/`에 UI, 상태 관리, 서비스 계층 분리
- 대화, 메시지, 태그, 프로젝트 모델 정의
- SQLite repository 구현
- Secure Storage service 구현
- AI provider service 구현
- Markdown export service 구현
- 보안 설정 및 앱 잠금 UI 구현

플랫폼별 기능은 다음 플러그인을 검토한다.

- SQLite: `sqflite` 또는 Drift
- DB 암호화: SQLCipher 지원 패키지
- Secure Storage: `flutter_secure_storage`
- 생체 인증: `local_auth`
- 파일 Export/Share: `path_provider`, `share_plus`, 파일 저장 패키지

## 영향
### 장점
- iOS와 Android를 하나의 코드베이스로 빠르게 개발할 수 있다.
- Web과 Desktop 확장 가능성을 확보할 수 있다.
- UI 일관성을 유지하기 쉽다.
- PRD의 V1 기능을 빠르게 프로토타이핑하고 검증할 수 있다.
- 로컬 저장, 보안 저장소, 생체 인증 등 필요한 플러그인 생태계가 존재한다.

### 단점
- 일부 고급 네이티브 기능은 플랫폼 채널 구현이 필요할 수 있다.
- 앱 크기가 네이티브 앱보다 커질 수 있다.
- Web/Desktop 지원 시 모바일과 다른 UX를 별도로 조정해야 한다.
- SQLCipher, Secure Storage 등 보안 관련 플러그인은 플랫폼별 검증이 필요하다.

## 리스크 대응
- 초기에는 플러터 공통 코드로 V1 기능을 구현하되, 보안/저장소 기능은 서비스 계층으로 분리한다.
- 플랫폼별 차이가 큰 기능은 인터페이스를 먼저 정의하고 구현체를 분리한다.
- SQLite, Secure Storage, Biometric Auth는 실제 기기에서 테스트한다.
- Web은 핵심 모바일 기능의 보조 채널로 두고, 보안 민감 기능은 모바일 우선으로 검증한다.

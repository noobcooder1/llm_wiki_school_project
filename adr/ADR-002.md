# ADR-002: 사용자 API 키 직접 사용 전략 채택

## 결론
LLM Wiki는 앱 운영자가 보유한 공용 API 키를 사용하는 대신, 사용자가 자신의 API 키를 직접 입력해 사용하는 BYOK(Bring Your Own Key) 전략을 채택한다.

이 결정을 한 이유는 AI API 비용 폭증과 악성 사용자의 abuse(남용) 위험을 줄이고, 사용자의 대화 데이터와 API 키가 제품 서버를 거치지 않도록 하기 위해서다. BYOK 구조를 사용하면 앱은 AI 비용 부담보다 지식 저장, 검색, 보안, 내보내기 경험에 집중할 수 있다.

## 결정 ---(좀 더 자세한 이유)
LLM Wiki는 BYOK(Bring Your Own Key) 전략을 채택한다.

사용자는 자신이 발급받은 API 키를 앱에 입력하고, 앱은 해당 Key를 이용해 AI provider에 직접 요청한다.

지원 계획은 다음과 같다.

- 첫 번째 개발 단계: OpenAI API 키
- 두 번째 개발 단계: Anthropic Claude API 키
- 두 번째 개발 단계: Google Gemini API 키

API 키 저장 정책은 다음과 같다.

- iOS에서는 Keychain에 저장한다.
- Android에서는 Keystore 기반 Secure Storage에 저장한다.
- API 키를 앱 서버에 저장하지 않는다.
- API 키를 평문으로 로컬 DB에 저장하지 않는다.
- 사용자가 원하면 API 키를 삭제하거나 교체할 수 있어야 한다.

## 결정 이유
BYOK를 선택한 이유는 비용 통제, 보안, 사용자 데이터 통제권 때문이다.

LLM Wiki는 AI 대화를 저장하고 지식화하는 앱이지, AI API 비용을 대신 부담하는 SaaS 모델이 핵심이 아니다. 앱 운영자가 모든 사용자의 AI 비용을 부담하면 무료 플랜 운영이 어렵고, 구독 모델을 설계하더라도 사용량 기반 비용 예측이 어려워진다.

BYOK를 사용하면 사용자의 AI 사용량과 비용은 사용자의 provider 계정에서 관리된다. 앱은 지식 저장, 검색, 분류, Export, 보안 UX에 집중할 수 있다.

보안 측면에서도 BYOK는 유리하다. 사용자 대화를 제품 서버로 보내지 않고, 앱에서 provider로 직접 요청하는 구조를 만들 수 있기 때문이다. 이는 PRD의 "사용자 API 키 서버 전송 금지", "사용자 대화 로그 서버 저장 금지" 요구사항과도 일치한다.

또한 BYOK는 장기적으로 여러 모델을 지원하기 쉽다. 사용자는 자신이 선호하는 provider의 Key를 입력하고, 앱은 provider별 호출 어댑터를 통해 확장할 수 있다.

## 상태
채택됨

## 배경
LLM Wiki 앱은 OpenAI API를 시작으로 Claude, Gemini 등 여러 AI 모델을 활용할 예정이다.

AI 모델 호출 방식은 크게 두 가지가 있다.

- 앱 운영자가 서버에 API 키를 보관하고 모든 사용자의 요청을 대신 처리한다.
- 사용자가 자신의 API 키를 직접 입력하고 앱이 해당 Key로 AI provider에 직접 요청한다.

LLM Wiki는 개인 지식 관리 앱이며, 사용자의 대화 내용이 민감할 수 있다. 따라서 AI 요청 과정에서도 사용자의 대화가 제품 서버를 거치지 않는 구조가 중요하다.

앱 자체 서버 키를 사용하는 경우 다음 문제가 발생할 수 있다.

- 사용량이 늘어날수록 운영자의 API 비용이 빠르게 증가한다.
- 악성 사용자가 자동화된 요청을 보내면 비용 폭탄이나 abuse 문제가 발생할 수 있다.
- 사용자별 rate limit, 사용량 제한, 결제 정책을 별도로 구현해야 한다.
- AI 요청이 제품 서버를 거치게 되어 대화 로그를 서버에서 처리해야 할 가능성이 커진다.
- OpenAI, Claude, Gemini 등 provider가 늘어날수록 서버 측 라우팅과 키 관리가 복잡해진다.


## 검토한 대안
### 제품 소유 API 키
앱 운영자가 서버에 API 키를 보관하고 모든 요청을 대행하는 방식이다.

사용자 입장에서는 가장 간단하지만, 운영 비용과 abuse 위험이 크다. 대화가 서버를 거쳐야 하므로 LLM Wiki의 local-first 보안 철학과 맞지 않는다.

### 사용자 토큰 기반 프록시 서버
사용자는 앱 계정으로 로그인하고, 서버가 내부적으로 provider API를 호출하는 방식이다.

구독 상품과 사용량 제한을 통합하기 쉽지만, 서버가 사용자 대화 데이터를 처리하게 된다. 또한 서버 장애 시 AI 기능 전체가 중단될 수 있다.

### 사용자 API 키 직접 사용
사용자가 자신의 Key를 앱에 저장하고 직접 provider를 호출하는 방식이다.

초기 설정 진입장벽은 있지만, 비용과 데이터 통제권 측면에서 LLM Wiki의 방향과 가장 잘 맞는다.

## 예상 구현
첫 번째 개발 단계에서는 다음 구현을 예상한다.

- 설정 화면에서 OpenAI API 키 입력
- 입력된 Key 형식 기본 검증
- Keychain/Keystore 기반 Secure Storage 저장
- 앱 실행 중 provider 요청 시 Secure Storage에서 Key를 읽어 사용
- Key 저장 여부만 UI에 표시하고 실제 Key 값은 노출하지 않음
- 사용자가 Key 삭제 또는 교체 가능

Provider 확장 구조는 다음을 예상한다.

- `AiProvider` 인터페이스 정의
- `OpenAiProvider` 구현
- 두 번째 개발 단계에서 `AnthropicProvider`, `GeminiProvider` 추가
- provider별 모델 목록, 요청 파라미터, rate limit 처리 분리

## 영향
### 장점
- 앱 운영자의 AI API 비용 부담이 줄어든다.
- 사용자 데이터와 API 키에 대한 통제권이 사용자에게 있다.
- 다양한 AI provider를 점진적으로 추가하기 쉽다.
- 서버에 사용자 대화 로그와 API 키를 저장하지 않는 보안 정책을 유지할 수 있다.
- Premium 구독은 AI 호출 비용이 아니라 고급 지식 관리 기능에 집중할 수 있다.

### 단점
- 일반 사용자는 API 키 발급 과정을 어렵게 느낄 수 있다.
- 초기 온보딩 UX가 복잡해질 수 있다.
- 사용자의 provider 계정 결제 상태나 rate limit 문제를 앱이 직접 해결할 수 없다.
- Key가 만료되거나 삭제되면 AI 채팅 기능이 실패할 수 있다.

## 리스크 대응
- API 키 발급 가이드를 앱 안에서 짧고 명확하게 제공한다.
- Key가 없어도 저장된 지식 검색, 마크다운 내보내기 등 핵심 기능은 사용할 수 있게 한다.
- Key 오류 메시지는 provider별로 이해하기 쉽게 변환한다.
- 두 번째 개발 단계 이후에는 선택적으로 "앱 제공 크레딧" 또는 "Premium 포함 사용량" 모델을 검토할 수 있다.
